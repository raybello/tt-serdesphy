# Analog/Digital Dual-Flow Framework

## Goal

Every analog block under `src/analog/` needs to exist in (at least) two
forms that must stay behaviorally consistent but are produced by completely
different toolchains:

1. **Behavioral view** — synthesizable-looking Verilog (what's there today),
   used for full-chip digital simulation (cocotb/UVM), fast regression, and
   as a synthesis stand-in.
2. **Circuit view** — a real transistor-level design, captured as an xschem
   schematic, verified in ngspice, and laid out in magic/klayout, ending in a
   DRC/LVS-clean GDS with an extracted netlist.

The chip build needs to pick the *behavioral* view for RTL sim/synthesis and
the *circuit* view (as a hard macro: GDS + LEF + extracted netlist + a
timing/power abstract) for the final tapeout, without hand-editing the
top-level netlist to swap between them, and without the two views silently
drifting apart.

## Directory layout

Extend each `src/analog/ana_*/<block>/` directory into a per-cell package.
Using the PLL VCO as the running example:

```
src/analog/ana_pll/serdesphy_ana_pll_vco/
├── behavioral/
│   └── serdesphy_ana_pll_vco.v          # today's file, moved here verbatim
├── schematic/
│   ├── serdesphy_ana_pll_vco.sch        # xschem schematic (source of truth for the circuit)
│   └── serdesphy_ana_pll_vco.sym        # xschem symbol (pin list must match the Verilog port list)
├── spice/
│   ├── serdesphy_ana_pll_vco.spice      # netlist exported from xschem (generated, not hand-edited)
│   ├── tb_vco_freq_sweep.spice          # ngspice testbench: Kvco / tuning-range sweep
│   ├── tb_vco_startup.spice             # ngspice testbench: startup transient, vco_ready timing
│   └── corners.include                  # PVT corner definitions (tt/ff/ss, 27C/-40C/85C, 1.62-1.98V)
├── layout/
│   ├── serdesphy_ana_pll_vco.mag        # magic layout (source of truth for silicon)
│   └── serdesphy_ana_pll_vco.gds        # exported GDS (generated)
├── extracted/
│   ├── serdesphy_ana_pll_vco.lvs.spice  # magic-extracted netlist (post-layout, for LVS)
│   └── serdesphy_ana_pll_vco.pex.spice  # parasitic-extracted netlist (for post-layout sim)
├── abstract/
│   ├── serdesphy_ana_pll_vco.lef        # abstract view for digital P&R (pins + obstruction, no internals)
│   └── serdesphy_ana_pll_vco.lib        # optional: liberty timing/power view if the block has digital-ish timing arcs
└── view.json                            # manifest — see below
```

This mirrors the structure `src/analog/ana_pll/`, `ana_tx/`, `ana_rx/`,
`ana_common/` already use, just one level deeper, per cell. Cells that will
never get a custom layout (pure placeholders like
`serdesphy_ana_loopback_switch` might legitimately stay digital gates driven
by standard cells) can skip `schematic/`, `spice/`, `layout/`, `extracted/`
and just keep `behavioral/` — the manifest below records that decision
explicitly instead of it being ambiguous.

### `view.json` manifest

One small JSON file per cell records which views exist and their
verification status, so tooling (and this documentation) never has to guess:

```json
{
  "cell": "serdesphy_ana_pll_vco",
  "port_list_hash": "sha1 of the Verilog module port declaration",
  "views": {
    "behavioral": { "path": "behavioral/serdesphy_ana_pll_vco.v", "status": "golden" },
    "schematic":  { "path": "schematic/serdesphy_ana_pll_vco.sch", "status": "not_started" },
    "spice":      { "path": "spice/serdesphy_ana_pll_vco.spice", "status": "not_started" },
    "layout":     { "path": "layout/serdesphy_ana_pll_vco.mag", "status": "not_started" },
    "gds":        { "path": "layout/serdesphy_ana_pll_vco.gds", "status": "not_started" },
    "lvs_clean":  false,
    "drc_clean":  false,
    "pex_matches_spice": false
  },
  "pdk": "sky130A",
  "target_for_tapeout": "circuit"
}
```

`status` values: `golden` (verified reference), `wip`, `not_started`,
`deprecated`. `target_for_tapeout` says which view the GDS-merge step should
actually pull in for this specific project's submission — this lets you
tape out with some blocks still behavioral-in-name-only if a schedule
forces it, as an explicit, visible decision rather than an accident.

A single top-level `src/analog/analog_views.json` (generated by concatenating
every `view.json`) gives one glanceable table of where every analog block
stands — this is the file the `01-spec-vs-implementation.md` "what's left to
do" section should eventually be auto-checked against.

## Toolchain per view

| Stage | Tool | Input | Output |
|---|---|---|---|
| Schematic capture | **xschem** | sky130 device symbols (`sky130_fd_pr`) | `.sch` (source of truth), `.sym` |
| Circuit simulation | **ngspice** | `.sch` netlisted via xschem, `sky130.lib.spice` corner models | transient/AC/noise/Monte-Carlo results |
| Netlist export | xschem's `netlist` command | `.sch` | `.spice` (flat or hierarchical netlist, generated — never hand-edit) |
| Layout | **magic** | device generators / hand-drawn geometry, guided by the SPICE netlist | `.mag` (source of truth for silicon), `.gds` |
| DRC | **magic** DRC or **klayout** DRC (sky130A rule deck) | `.gds` | pass/fail + report |
| LVS | **netgen** (magic-extract vs. schematic netlist) or klayout LVS | `.mag`-extracted netlist vs. `spice/*.spice` | pass/fail + report |
| Parasitic extraction | **magic** `extract`/`ext2spice`, or klayout+magic combo | `.mag` | `extracted/*.pex.spice` |
| Post-layout re-sim | **ngspice** | `.pex.spice` + same testbenches as pre-layout | confirms layout didn't break the electrical spec |
| Digital abstract | **magic** `lef write` | `.mag` | `abstract/*.lef` |

All of this is standard open-source SKY130 flow (the same toolchain the
`actions/gds` LibreLane flow in this repo already assumes for the digital
side); the addition here is just structuring it per-analog-cell instead of
per-chip.

## Behavioral ⇄ circuit consistency

The two views will inevitably be developed at different times by different
processes (RTL now, circuits later). Two things keep them from silently
diverging:

1. **Port-list hash check.** `view.json`'s `port_list_hash` is computed from
   the Verilog module's port declaration. A pre-commit/CI check re-hashes
   `behavioral/*.v` and fails if it no longer matches — this catches "someone
   added a port to the behavioral model and forgot the schematic symbol
   needs the same port" (or vice versa) immediately, rather than at final
   LVS.
2. **Cross-domain equivalence testbenches.** For each cell, one lightweight
   testbench asserts the same *behavioral claim* against both views and
   diffs the result:
   - Behavioral (Verilog, via cocotb or plain `iverilog`/`verilator`): run
     the existing digital testbench, capture key waveforms (e.g. VCO period,
     lock latency, output swing as a 0/1 proxy).
   - Circuit (ngspice): run the equivalent SPICE testbench, capture the same
     quantities (measured VCO period via `.measure`, lock/settle time,
     actual output swing in mV).
   - A small Python script (`scripts/compare_views.py`, one per cell type)
     asserts the two are within an agreed tolerance (e.g. VCO center
     frequency within 5%, lock time within 2×).

   This is what upgrades a behavioral model from `wip` to `golden` in
   `view.json` — "golden" should mean "matches its circuit view within
   tolerance," not just "compiles."

3. **Until a circuit view exists**, the behavioral model is the only
   available truth, which is exactly today's state (see
   `01-spec-vs-implementation.md` §3.6 for the PLL/CDR case) — that's fine,
   but `view.json` marking those views `not_started` makes the *limitation*
   explicit and searchable instead of something a reviewer has to
   rediscover by reading source.

## Selecting the right view at build time

Three consumers need different views of the same cell, and none of them
should require editing `serdesphy_pma.v`:

### 1. RTL simulation (cocotb / UVM / `iverilog`/`verilator`)
Always uses `behavioral/*.v`. No change needed from today — this is what the
existing sim flow already does, since `src/analog/ana_pll/serdesphy_ana_pll.v`
etc. currently *are* the behavioral files (this framework just proposes
moving them one directory level deeper for consistency; a compatibility
`src/analog/ana_pll/serdesphy_ana_pll_vco.v` can stay as a thin `` `include ``
of the new path if churn should be minimized initially).

### 2. Digital synthesis (Yosys/OpenROAD via LibreLane, `actions/gds/`)
Analog cells must be **black-boxed**, not synthesized from the behavioral
Verilog (today's `` `ifdef SYNTHESIS `` constant-0 placeholders in
`serdesphy_ana_pll_vco.v`/`serdesphy_ana_cdr_vco.v` already gesture at this,
but a stub that just drives `1'b0` isn't a real black-box — Yosys will still
try to synthesize whatever logic *is* there for cells without that guard,
e.g. the charge pump, loop filter, and phase detector today). The
recommended mechanism:

- A `blackbox/<cell>.v` stub per analog cell: just the module port
  declaration with `(* blackbox *)` (Yosys attribute), no internal logic.
- LibreLane config (`src/config.json` / the per-run config) points
  `VERILOG_FILES`/`EXTRA_LEFS`/`EXTRA_LIBS` at the blackbox stubs +
  `abstract/*.lef` (+ `.lib` if timing arcs matter) for every analog cell
  whose `target_for_tapeout` is `"circuit"`, and at the plain behavioral file
  for any cell still `"behavioral"` (i.e. "we're taping out with a digital
  stand-in for now" — should be rare and explicit).
- This is exactly how the existing LibreLane flow already needs to treat any
  hard macro (e.g. an SRAM); analog blocks are just another hard macro from
  the digital P&R tool's point of view.

### 3. GDS merge (final tapeout)
The chip-level GDS merge step (already part of `actions/gds/`) additionally
streams in `layout/<cell>.gds` for every `"circuit"`-targeted cell at its
placed location (from the floorplan/macro-placement step), on top of the
digital P&R output. `netgen`/klayout LVS then runs **chip-level**, comparing
the full merged GDS against the full merged (digital netlist + analog
extracted netlists) schematic-equivalent netlist — this is the final gate
before submission.

## Make targets (proposed)

A small `Makefile` per cell (or one parameterized top-level `Makefile`
invoked as `make CELL=serdesphy_ana_pll_vco <target>`) standardizes the
flow so it's the same muscle memory for every block:

```
make sim-behavioral   # cocotb/iverilog run against behavioral/*.v
make sim-spice        # ngspice run of every spice/tb_*.spice, dumps .measure results
make netlist          # xschem -> spice/<cell>.spice (regenerate from schematic)
make drc              # magic/klayout DRC on layout/<cell>.gds
make lvs              # netgen: layout/<cell>.mag extracted vs spice/<cell>.spice
make pex              # magic ext2spice -> extracted/<cell>.pex.spice
make sim-pex          # ngspice run of spice/tb_*.spice against the PEX netlist
make lef              # magic lef write -> abstract/<cell>.lef
make compare-views    # scripts/compare_views.py: behavioral vs spice/pex results
make golden           # runs drc+lvs+sim-pex+compare-views, and if all pass, bumps view.json status to "golden"
```

CI should run `sim-behavioral` for every cell on every commit (cheap, fast),
and `drc`/`lvs`/`sim-spice` on demand or nightly once schematics start
landing (SPICE sims and magic DRC/LVS are slow enough that they don't belong
in the fast inner loop).

## Rollout order

Don't try to stand up all six directories (`behavioral/schematic/spice/
layout/extracted/abstract`) for every analog cell at once. Suggested order,
matching the priority blocks called out in the request and detailed in their
own plan docs:

1. **PLL** (`pll/README.md`) — highest schedule risk, most complex loop, and
   every other clocked block depends on it.
2. **TX differential driver** (`tx_driver/README.md`) — simplest of the four
   (essentially a buffer with programmable swing), good first end-to-end
   proof of the whole framework (schematic → GDS → LVS-clean) before tackling
   the harder blocks.
3. **RX differential receiver** (`rx_receiver/README.md`).
4. **CDR + CDR VCO** (`cdr_vco/README.md`) — most complex, depends on
   patterns established by the PLL VCO work.

Supporting cells (`bias_generator`, `loopback_switch`, `analog_debug_buffer`)
can follow once the pattern is proven, and may turn out not to need a custom
layout at all (e.g. the loopback switch might just be a standard-cell mux
plus real analog switches, in which case its `view.json` legitimately never
grows a `schematic/`/`layout/` beyond a trivial pass-gate).
